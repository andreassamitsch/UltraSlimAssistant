# Work cycle 10 — signing, background policy and managed alternative (2026-11-26)

## Verified public documentation and source

- Tizen native [security privileges](https://github.com/Samsung/tizen-docs/blob/master/docs/application/native/reference/security-privileges.md), blob fcf729a9fc738f352b305fe011762659e3c91cc3, line 149, classifies recorder as public. A normal app on a compatible supported target does not inherently require a vendor platform certificate for this API. This does not confer capture access on HW-S800D or establish that a headless product accepts the app.
- [Signing certificates](https://github.com/Samsung/tizen-docs/blob/master/docs/application/native/guides/concepts/signing-certificates.md), blob 4de0c6f640d54ab6d8fdcf5cfc0a81840dca9f47, distinguishes author identity, distributor authorization, public/partner/platform privileges, and vendor-controlled application acceptance. [Samsung TV certificates](https://developer.samsung.com/smarttv/develop/getting-started/setting-up-sdk/creating-certificates.html) require the target DUID and Samsung certificate extension. No evidence that this product is eligible for that certificate flow; a SmartThings device ID is not a DUID. No certificate requested or credentials handled.
- [Service lifecycle guide](https://github.com/Samsung/tizen-docs/blob/master/docs/application/native/guides/applications/service-app.md), blob 12a1c4080a672f44cb954b96eca5a6e0efad6ce2, explains suspension and background categories. [Application overview](https://github.com/Samsung/tizen-docs/blob/master/docs/application/native/guides/applications/overview.md), blob c58182cf3cbca8e98da7d0527ff6f9c70b7867e2, lists media for background recording/playback, background-network for network operations. Declaration alone does not establish perpetual wakeword processing, automatic restart or authorization on the soundbar.
- Samsung's [TV testing FAQ](https://developer.samsung.com/smarttv/develop/faq/application-testing.html) Q25 describes restrictions on native C TPKs in its Web app workflow. Separately, [TV .NET application documentation](https://developer.samsung.com/smarttv/develop/tizen-net-tv/getting-started/creating-net-tv-applications.html) explicitly describes installing .NET TPKs on supported TVs. Do not generalize the Web FAQ to every TPK type. [TV .NET FAQ](https://developer.samsung.com/smarttv/develop/faq/tizen-net-tv.html) Q3 limits native interop; Q5 confines TV .NET support to supported Smart TVs. Neither proves soundbar support.
- Actual upstream TizenFX main source [ServiceApplication.cs](https://github.com/Samsung/TizenFX/blob/main/src/Tizen.Applications.Service/Tizen.Applications/ServiceApplication.cs), blob 428225acd86cd20a57db8495e9265d9c37582613, provides managed background service class. [AudioCapture.cs](https://github.com/Samsung/TizenFX/blob/main/src/Tizen.Multimedia.AudioIO/AudioIO/AudioCapture.cs), blob b924a996ed2abe6b1fd32fb53e2bd750a64f039b, defines AudioCapture and AsyncAudioCapture, recorder privilege annotations and data callback. Upstream main is not the exact Tizen 8 target runtime. Managed code is a conditional alternative if S800D has supported .NET deployment/runtime and these APIs; neither established.

## Decision matrix
- C native service: generic SDK header validation passed; owner developer connection, target certificate eligibility, CPU ABI, package acceptance and runtime permissions unresolved.
- Managed C# service: documented upstream service/capture APIs; additional unknown .NET runtime/profile and API presence on S800D. No rewrite until target evidence.
- Web app/service: Samsung TV route exists, but no soundbar Web app installation path or supported continuous background speech capture demonstrated. TV [personal preview service policy](https://developer.samsung.com/smarttv/develop/guides/smart-hub-preview/implementing-personal-preview.html) has a specific five-minute lifecycle limitation; not a universal Tizen service limit.

## Purchase gate and next action
Public recorder privilege removes the assumption that platform signing is inherently necessary for every microphone API. The actual unresolved gate is whether S800D exposes an authorized developer session and accepts an independently signed package in any appropriate profile. Keep hardware purchase on hold pending new model-specific evidence. Do not reuse vendor signing keys, change debug/update settings or bypass package checks. No target interaction, installation, recording, archive download or new build in this cycle. Further generic SDK research cannot prove target policy; prioritize new actual model-specific evidence (including same-family LS60D/Q800D/Q990D) over repeating the prior source scan.
