# Work cycle 5 — audio service boundaries and configuration (2026-11-26)

## Method
Read the private companion source tree and selected complete files directly. The tree contained 9,395 entries (including directories), not truncated. No new archive acquisition or target interaction. All evidence below is from the Q800D reference unless explicitly stated otherwise; actual HW-S800D routing and permissions remain unknown.

## Findings

1. **Firmware-specific ALSA configuration chain.** The MT8532 component (SHA256 4941bfbd57224d69bb56d9ef76e7071d3f230fe0f048276bad74c99159044dfc), mdp_alsa/swdsp/mas_thread/share/alsa/alsa.conf lines 6–24, blob 5ffea33f85d7396609c0d29c474fea155af8fbdb, loads system, vendor and user configuration. The vendor asound.conf (blob 8ffd32e5b6930377665c2e2ec6141dc3bf924237) includes aasound.conf, which includes the MT8532 platform appendix. The vendor startup script references private audio libraries. A normal application cannot be assumed to have the same ALSA namespace, libraries, permissions or routing. No runtime configuration change proposed.
2. **Separate speech input/output candidates.** aasound.conf (blob 81073ae8396f29444cafca0d9aa77923ba974b0f), lines 99–142, defines shared capture and FFP processing. The normal default capture is not FFP. Its voice-upload alias is a null PCM (lines 50–52); echo reference is not a microphone. asound.conf lines 34–43 defines avs_out as a plug backed by shared 48 kHz playback and channel mixing. This is a new explicit candidate for assistant output in the reference, not a confirmed Alexa service API or a supported endpoint for third-party apps. Use existing authorized playback or the official audio API first. The pre-AEC configuration is also distinct from the FFP path.
3. **Control APIs are kernel controls, not service discovery.** tzsb_control/tzsb_control_interface.c (blob b6f526ebd716734f5e7f4c180cc91ecfd10bcc56), lines 12–45, initializes audio input/output, decoder, ACM and postprocessing and registers ALSA SoC component controls. audio_input_control_interface.c (blob e4dd1b46e88a8d34b92e7f319af80dfddf1289d2), lines 298–343, registers source selection, digital input status, stream information and HDMI state callbacks. These are not a D-Bus service, remote API or third-party microphone permission mechanism. Do not write mixer controls or use raw devices as a substitute for permitted capture.
4. **Microphone privacy remains unresolved.** A targeted search for microphone mute, privacy, voice-command and wake-word terms in alsa_if_name_tzav.h, alsa_tzav.c, mt8532-afe-controls.c and three MICOM key/system/remote sources found no direct matches. This is limited negative evidence, not proof hardware mute is absent or not enforced. The firmware service binaries and vendor policy are not represented fully.
5. **Driver-level confirmation.** mt8532-sound3.c (blob 4384734a70250191a22d1532b0152ae7aa57ceaf) declares a DMIC capture backend and UL9 capture frontend. mt8532-afe-pcm3.c (blob cd21972681356df775431081c5ab247e2c46920a) includes DMIC signal routes. These validate the reference hardware design but do not grant application access. Some configuration paths still refer to unresolved aliases and nonstandard plugins; source snapshot excludes some file types. No claim that all ALSA nodes or plugins are present on S800D.

## Integration decision
Maintain separate gates:
- M1: supported, owner-accessible execution and valid app authorization. No new supported path identified.
- M2: use native feature queries and metadata-only Sound Manager inventory; verify permissions and physical mute behavior before any recording. Never assume a readable mixer/control means capture is permitted.
- M3: after explicit recording approval, prefer authorized processed speech capture through documented APIs; only evaluate vendor FFP as a supported application-accessible option if actual evidence warrants it. Distinguish application playback from firmware-internal avs_out. Validate coexistence with existing audio and avoid modifying vendor services.

The next high-value research question is whether any documented S800D service or supported application interface exposes native application lifecycle or microphone capability. Repeated analysis of DSP internals cannot alone resolve M1. If no such interface can be established, the native path remains unverified; independent HA voice satellite remains a fallback, not the current project goal.

No new code installed or device behavior changed. No signing material, private diagnostic data, or sensitive vendor configuration copied into the public development repository.
